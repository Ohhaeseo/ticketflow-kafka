# 데이터베이스

> 요구사항 기준: [PRD §9 데이터 모델](../prd.md#9-데이터-모델). 이 문서는 **실제 마이그레이션 결과**를 기록합니다.

## 마이그레이션 이력

| 버전 | 파일 | 내용 | 주차 |
| --- | --- | --- | --- |
| V1 | `db/migration/V1__create_events.sql` | `events` 테이블, CHECK 제약 3개 | 1주 ✅ |
| V2 | `db/migration/V2__create_users_and_reservations.sql` | `users`, `reservations`, UNIQUE 2개, 상태 CHECK | 2주 ✅ |

| V5 | `db/migration/V5__create_dead_letter_messages.sql` | `dead_letter_messages` (DLT 감사 이력) | 6주 ✅ |

- 마이그레이션 위치: `backend/src/main/resources/db/migration/`. 시드는 `db/seed/`에 두고 `local` 프로필에서만 Flyway 위치에 추가한다 (`spring.flyway.locations`).
- 시드는 반복 실행(repeatable) 마이그레이션이며 `ON CONFLICT DO NOTHING`이라 여러 번 실행해도 결과가 같다.
- JPA는 `ddl-auto: validate`로 엔티티와 스키마가 맞는지만 확인한다. 스키마 변경은 Flyway로만 한다.
- 이미 적용된 마이그레이션 파일은 수정하지 않고 새 버전을 추가한다.

## 테이블 정의

### `events`

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| `id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` |
| `title` | `VARCHAR(200)` | NOT NULL |
| `total_tickets` | `INTEGER` | NOT NULL |
| `remaining_tickets` | `INTEGER` | NOT NULL |
| `sales_start_at` | `TIMESTAMPTZ` | NOT NULL |
| `sales_end_at` | `TIMESTAMPTZ` | NOT NULL |

| 제약 이름 | 조건 | 목적 |
| --- | --- | --- |
| `ck_events_total_tickets` | `total_tickets >= 0` | 음수 총 수량 방지 |
| `ck_events_remaining_tickets` | `remaining_tickets BETWEEN 0 AND total_tickets` | **초과 판매의 마지막 방어선** (FR-INV-02) |
| `ck_events_sales_period` | `sales_start_at < sales_end_at` | 잘못된 판매 기간 방지 |

검증 테스트: `backend/src/test/java/com/ticketflow/event/EventTableConstraintTest.java`

### `users`

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| `id` | `BIGINT` | PK, `GENERATED BY DEFAULT AS IDENTITY` (시드가 id를 직접 지정) |
| `nickname` | `VARCHAR(50)` | NOT NULL. 시드 값 `test-user-0001` 형식 |

실제 개인정보는 저장하지 않는다.

### `reservations`

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| `id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY` |
| `event_id` | `BIGINT` | NOT NULL, FK → `events.id` |
| `user_id` | `BIGINT` | NOT NULL, FK → `users.id` |
| `idempotency_key` | `VARCHAR(100)` | NOT NULL |
| `request_hash` | `VARCHAR(64)` | NOT NULL. 정규화한 요청 본문의 SHA-256 hex |
| `status` | `VARCHAR(20)` | NOT NULL |
| `failure_reason` | `VARCHAR(50)` | `FAILED`일 때 원인 |
| `created_at`, `updated_at` | `TIMESTAMPTZ` | NOT NULL. 애플리케이션이 마이크로초로 잘라 저장 |

| 제약·인덱스 | 내용 | 목적 |
| --- | --- | --- |
| `uk_reservations_event_user` | `UNIQUE (event_id, user_id)` | 같은 사용자의 같은 공연 예약 1건 (FR-RSV-03) |
| `uk_reservations_user_idempotency_key` | `UNIQUE (user_id, idempotency_key)` | 같은 키 재전송은 1건 (FR-RSV-02) |
| `ck_reservations_status` | `status IN ('QUEUED','CONFIRMED','SOLD_OUT','FAILED')` | 정의되지 않은 상태 방지 |
| `idx_reservations_status_created_at` | `(status, created_at)` | 상태별 처리 지연 조회 (5주차 지표) |

`(user_id, idempotency_key)` UNIQUE 인덱스가 `user_id`로 시작하므로 내 예약 목록 조회에도 쓰인다.

## 예약 접수 쿼리

```sql
INSERT INTO reservations
    (event_id, user_id, idempotency_key, request_hash, status, created_at, updated_at)
VALUES (:eventId, :userId, :idempotencyKey, :requestHash, 'QUEUED', :now, :now)
ON CONFLICT DO NOTHING
RETURNING id;
```

- 두 UNIQUE 제약 중 하나라도 걸리면 아무것도 저장하지 않고 행을 반환하지 않는다. 예외가 나지 않으므로 트랜잭션이 깨지지 않는다.
- 경쟁하는 트랜잭션이 아직 커밋 전이면 PostgreSQL이 그 트랜잭션이 끝날 때까지 기다린 뒤 판정한다. 이어지는 `SELECT`는 READ COMMITTED에서 새 스냅샷을 쓰므로 먼저 저장된 예약을 읽을 수 있다.
- 검증 테스트: `ReservationIdempotencyTest` — 같은 요청 10개 동시 전송 → 202 1회, 200 9회, 예약 1건.

### `outbox_events`

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| `id` | `BIGINT` | PK, `GENERATED ALWAYS AS IDENTITY`. 발행 순서 |
| `message_id` | `UUID` | NOT NULL, UNIQUE. 저장 시 생성, 재발행해도 같은 값 |
| `reservation_id` | `BIGINT` | NOT NULL, FK → `reservations.id` |
| `event_type` | `VARCHAR(100)` | NOT NULL. 현재 `ReservationRequested` |
| `message_key` | `VARCHAR(100)` | NOT NULL. Kafka key (`eventId`) |
| `payload` | `TEXT` | NOT NULL. 메시지 JSON (PRD Q7) |
| `created_at` | `TIMESTAMPTZ` | NOT NULL |
| `published_at` | `TIMESTAMPTZ` | 브로커 ack 후 채움. NULL이면 미발행 |

인덱스 `idx_outbox_events_unpublished (id) WHERE published_at IS NULL` — Relay의 `WHERE published_at IS NULL ORDER BY id LIMIT n` 조회용. 발행된 행은 인덱스에서 빠진다.

### `processed_messages`

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| `message_id` | `UUID` | PK. Outbox가 만든 메시지 ID |
| `reservation_id` | `BIGINT` | NOT NULL, FK → `reservations.id`, 인덱스 |
| `outcome` | `VARCHAR(30)` | NOT NULL. `CONFIRMED` / `SOLD_OUT` / `FAILED` / `SKIPPED_ALREADY_PROCESSED` |
| `processed_at` | `TIMESTAMPTZ` | NOT NULL |

- 원본 PRD 컬럼에 `outcome`을 더했다. 어떤 메시지가 어떤 결과를 냈는지 운영자가 추적할 수 있게 하려는 것이다.
- 같은 `message_id`가 다시 오면 이 테이블을 보고 건너뛴다. 이때는 이력을 더 남기지 않는다 (PK).
- 처리 트랜잭션이 롤백되면 이력도 함께 사라지므로, 실패한 메시지는 재전달 시 다시 처리된다.

### `dead_letter_messages`

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| `id` | `BIGINT` | PK |
| `original_topic`, `original_partition`, `original_offset` | `VARCHAR(200)`, `INTEGER`, `BIGINT` | NOT NULL, UNIQUE 묶음 (같은 원본은 한 번만 기록) |
| `message_key`, `payload` | `VARCHAR(200)`, `TEXT` | 원본 그대로 (깨진 JSON도 보존) |
| `exception_class`, `exception_cause_class`, `exception_message` | `VARCHAR(300)`, `VARCHAR(300)`, `TEXT` | DLT 헤더에서 옮김 |
| `dlt_partition`, `dlt_offset` | `INTEGER`, `BIGINT` | DLT 토픽에서의 위치 |
| `received_at` | `TIMESTAMPTZ` | NOT NULL, 인덱스 |

FK가 없는 것은 의도한 설계다. 깨진 메시지는 어떤 예약에도 연결되지 않을 수 있다.

## Consumer 처리 쿼리 (3~4주차, 11-21 개선 ✅)

`ReservationProcessor`가 **한 트랜잭션** 안에서 메시지마다 아래 순서로 실행한다. 메시지당 SQL 왕복은 **3번**이다. 11-21 이전에는 5~6번이었다 (재고 감소, 재고 상태 조회, 상태 변경, 이력 기록을 따로 실행).

```sql
-- 1. 예약 행 잠금. 같은 예약에 대한 메시지는 여기서 줄을 선다
SELECT id, event_id, status FROM reservations WHERE id = :id FOR UPDATE;

-- 2. 같은 message_id를 이미 처리했으면 끝낸다 (MSG-01: Kafka 재전달, Outbox 재발행)
--    잠금을 얻은 뒤 새 문장으로 조회해야, 동시에 처리된 같은 메시지의 커밋 결과가 보인다
SELECT EXISTS (SELECT 1 FROM processed_messages WHERE message_id = :messageId);

-- (status가 QUEUED가 아니면 재고를 건드리지 않고 이력만 남긴다: 다른 message_id로 온 중복)

-- 3. 재고 감소 → 결과 판정 → 상태 변경 → 이력 기록을 한 문장으로 (ReservationOutcomeRepository)
WITH stock AS (
    UPDATE events SET remaining_tickets = remaining_tickets - 1
     WHERE id = :eventId AND remaining_tickets > 0
       AND sales_start_at <= CURRENT_TIMESTAMP AND sales_end_at > CURRENT_TIMESTAMP
    RETURNING id
),
decision AS (
    SELECT CASE WHEN EXISTS (SELECT 1 FROM stock) THEN 'CONFIRMED'
                WHEN e.remaining_tickets = 0
                  OR (e.sales_start_at <= CURRENT_TIMESTAMP AND e.sales_end_at > CURRENT_TIMESTAMP) THEN 'SOLD_OUT'
                ELSE 'FAILED' END AS outcome
      FROM events e WHERE e.id = :eventId
),
updated AS (
    UPDATE reservations r SET status = d.outcome,
           failure_reason = CASE WHEN d.outcome = 'FAILED' THEN 'SALES_CLOSED' END, updated_at = :now
      FROM decision d WHERE r.id = :reservationId AND r.status = 'QUEUED'
    RETURNING r.id
),
recorded AS (
    INSERT INTO processed_messages (message_id, reservation_id, outcome, processed_at)
    SELECT :messageId, :reservationId, d.outcome, :now FROM decision d
    RETURNING message_id
)
SELECT d.outcome, (SELECT count(*) FROM updated), (SELECT count(*) FROM recorded) FROM decision d;
```

- **판정 규칙:** 재고 감소가 1행이면 CONFIRMED. 0행이고 재고가 0이거나 판매 기간 안이면 SOLD_OUT. 판매 기간 안인데 감소가 실패했다면 다른 트랜잭션이 마지막 재고를 가져간 것이다. 그 외(판매 기간 밖, 재고 남음)는 FAILED + SALES_CLOSED (PRD Q3).
- **스냅샷:** `decision`의 `events` 조회는 이 문장의 스냅샷을 쓴다. 같은 트랜잭션에서 앞서 실행한 문장의 변경(배치 리스너가 앞 메시지에서 줄인 재고)은 보인다. 검증: `ReservationProcessorTest`의 배치 테스트 (티켓 1장에 2건 → CONFIRMED, SOLD_OUT).
- **실패 처리:** 반영된 행 수가 1이 아니면 애플리케이션이 예외를 던진다. 문장 안 어디서 실패해도 재고 감소·상태 변경·처리 이력이 함께 롤백된다 (FR-INV-03). 오프셋도 커밋되지 않아 메시지를 다시 받는다. 검증: `ReservationProcessorTest`에서 DB 트리거로 상태 변경을 실패시킨 뒤 재고가 원래대로인지 확인한다.
- **동시성:** 재고 1장에 여러 예약이 동시에 재고 감소에 도달하면 `events` 행 잠금 때문에 순서대로 실행된다. 뒤에 실행되는 UPDATE는 앞 트랜잭션이 커밋한 값(0)으로 `WHERE remaining_tickets > 0`을 다시 평가하므로 0행이 된다 (READ COMMITTED 재평가). 검증: `ReservationConcurrencyTest` (CON-02).
- **시각:** `CURRENT_TIMESTAMP`는 트랜잭션 시작 시각이다. 판매 기간 판정은 DB 시각 기준이다.

## 상태 전이

```text
QUEUED ──┬──> CONFIRMED   재고 감소 1행
         ├──> SOLD_OUT    재고 감소 0행, remaining_tickets = 0
         └──> FAILED      재고 감소 0행, 판매 기간 밖 (failure_reason = SALES_CLOSED)
```

모든 전이는 `WHERE status = 'QUEUED'` 조건을 붙여 최종 상태를 다시 바꾸지 않는다.

## 불변식 검증 쿼리

```sql
SELECT e.id,
       e.total_tickets,
       e.remaining_tickets,
       count(r.id) FILTER (WHERE r.status = 'CONFIRMED') AS confirmed,
       count(r.id) FILTER (WHERE r.status = 'SOLD_OUT')  AS sold_out,
       count(r.id) FILTER (WHERE r.status = 'QUEUED')    AS queued
  FROM events e
  LEFT JOIN reservations r ON r.event_id = e.id
 WHERE e.id = :eventId
 GROUP BY e.id;
-- 합격: remaining_tickets >= 0
--       confirmed <= total_tickets
--       confirmed + remaining_tickets = total_tickets   (MVP: 취소 없음)
--       queued = 0                                      (처리 완료 후)
```

테스트 헬퍼 `support/StockInvariant`가 같은 조건을 검사한다.

| --- | --- | --- |
| `OversellPreventionIntegrationTest` | 티켓 100장, 150명 동시 접수 (API → Outbox → Kafka → Consumer) | CONFIRMED 100, SOLD_OUT 50, 잔여 0, 처리 이력 150 |
| `ReservationConcurrencyTest` | 티켓 1장, 예약 8건 동시 처리 | CONFIRMED 1, SOLD_OUT 7, 음수 재고 없음 |
