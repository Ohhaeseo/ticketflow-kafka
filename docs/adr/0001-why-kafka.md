# ADR-0001: 예약 처리에 Kafka를 도입하는 이유

- **상태:** 채택 (Accepted)
- **날짜:** 2026-11-20
- **관련 문서:** [PRD §1.3 핵심 설계 원칙](../../prd.md#13-핵심-설계-원칙), [PRD §8 시스템 아키텍처](../../prd.md#8-시스템-아키텍처)

## 맥락

- 잔여 100장에 1,000명이 동시에 예약을 시도하면 요청이 짧은 시간에 몰린다.
- 요청마다 동기적으로 재고를 감소시키면 같은 `events` 행에 잠금 경합이 집중되고, 그 지연이 요청자 전체의 응답 시간으로 퍼진다.
- 초과 판매 방지는 어떤 방식을 택하든 **DB 원자적 갱신**으로 보장해야 한다. 메시징 도구는 이 보장을 대신하지 못한다.
- 포트폴리오 목표에는 at-least-once 전달, 중복 소비, Consumer 장애 같은 분산 처리 문제를 직접 재현하고 검증하는 것이 포함된다.

## 결정

1. API는 예약을 **접수만 하고 `202 Accepted`를 반환**한다. 예약(`QUEUED`)과 Outbox 행은 같은 DB 트랜잭션에 기록한다.
2. Outbox Relay가 미발행 행을 Kafka `reservation.requested.v1`로 발행한다 (key = `eventId`).
3. Consumer가 DB 트랜잭션 안에서 중복 확인 → 조건부 `UPDATE`로 재고 감소 → `CONFIRMED`/`SOLD_OUT` 전이를 수행하고, DB 커밋 후 오프셋을 커밋한다.
4. 정확성의 최종 근거는 PostgreSQL(조건부 UPDATE, CHECK, UNIQUE, `processed_messages`)이다.
5. Kafka는 로컬 단일 노드 KRaft로 운영한다. 고가용성은 이번 범위에서 다루지 않는다.

## 검토한 대안

| 대안 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 동기 DB 처리 (요청 트랜잭션에서 조건부 UPDATE) | 단순하고 결과가 즉시 나옴 | 피크 시 잠금 경합과 지연이 요청자에게 직접 전달됨 | **비교 기준선**으로 유지 (FR-BMK-01) |
| Redis 원자 연산 (DECR) + 비동기 저장 | 매우 빠름 | Redis와 DB 사이 정합성, 영속성, 재처리를 별도로 설계해야 함 | 채택하지 않음. Redis는 빈도 제한에만 사용 |
| RabbitMQ 등 큐 브로커 | 작업 큐 의미가 명확함, 메시지 단위 ack | 재소비(오프셋 되감기), 파티션 기반 확장 실험이 Kafka보다 제한적 | 채택하지 않음 |
| **Kafka + Transactional Outbox** | 비동기 완충, 재소비, Consumer 확장, 장애 복구 실험이 가능 | 운영 복잡도, 최종 결과까지 지연, 멱등 처리 필수 | **채택** |

## 결과

**얻는 것**

- 요청 폭주를 Kafka가 흡수하고 접수 API는 짧은 트랜잭션(INSERT 2건)만 수행한다.
- Consumer 중단·재시작, 중복 메시지, Outbox 재발행을 실험으로 재현할 수 있다.
- `api`/`worker` 프로필로 접수와 처리를 독립적으로 확장할 수 있다.

**감수하는 것**

- `202`는 접수일 뿐 확정이 아니다. 클라이언트는 상태 조회(polling)로 결과를 확인해야 한다.
- at-least-once 전달 때문에 모든 Consumer 처리를 멱등하게 만들어야 한다.
- key가 `eventId`이므로 인기 공연 하나의 처리는 파티션 하나에서 순차 처리된다 (PRD §10.3).
- 단일 노드 Kafka는 브로커 장애를 견디지 못한다.

**검증 방법**

- `docs/benchmark-report.md`에서 동기 방식과 같은 실험 조건으로 비교한다 (DoD-7). Kafka 방식이 항상 빠르다고 가정하지 않는다.
